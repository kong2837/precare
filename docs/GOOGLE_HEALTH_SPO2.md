# Google Health SpO₂ 조회 점검

`check_spo2`는 한국시간(Asia/Seoul) 기준 날짜 범위를 API 요청에 넣고,
`nextPageToken`이 없어질 때까지 모든 페이지를 조회한다. 측정 데이터는 DB에 저장하지 않는다.
출력에는 날짜별 페이지 수, API 원본 건수, 해당 날짜의 유효 필드 건수와 측정 시각 범위가 포함된다.
이름, 외부 사용자 식별자, 토큰 및 개별 SpO₂ 값은 출력하지 않는다.

변경된 코드를 해당 DB에 연결된 서버에 반영한 후 실행한다.

```bash
docker exec apop python manage.py check_spo2 \
  --user-id <USER_ID> \
  --start-date YYYY-MM-DD \
  --end-date YYYY-MM-DD
```

종료일도 조회에 포함된다. KST 하루는 해당 날짜 00:00 이상, 다음 날짜 00:00 미만으로
정의하고 UTC로 변환해 `oxygen_saturation.sample_time.physical_time`을 필터링한다.

- HTTP 200, 원본 0건: 해당 요청 조건에 대해 API가 데이터를 반환하지 않았다.
- 원본이 있으나 해당 날짜 건수가 적음: 시간·필드 오류 및 날짜 밖 건수를 확인한다.
- HTTP 401: 인증 재연결 또는 `--refresh-token` 옵션이 필요하다.
- HTTP 403: OAuth 권한 및 API 접근 설정을 확인한다.
- HTTP 429: 같은 페이지를 최대 3회 재시도한다. 아래 대기 정책을 따른다.
- 계정 없음: 명령이 연결한 DB와 대상 사용자의 `user_id`를 확인한다.
- 페이지 요청 실패: 빈 데이터로 취급하지 않고 명령을 실패 처리한다.

`--refresh-token`을 지정하면 HTTP 401에서 인증 토큰 갱신을 한 번 허용하며,
이 경우 계정의 토큰·만료 시각이 DB에서 변경될 수 있다. 헬스데이터는 저장하지 않는다.

정상 수집 함수 `get_spo2`도 같은 날짜·페이지 조회를 사용한다. 전체 조회에 성공한 뒤
기존 방식으로 분 단위 SpO₂를 저장하며, 어느 페이지라도 실패하면 부분 결과를 저장하지 않는다.
일별 평균 SpO₂를 분 단위 측정값으로 대체하지 않는다.

## HTTP 429 대기 및 재시도

자동 수집, 조회 점검, 수동 복구는 모두 같은 SpO₂ 조회 함수를 사용한다.

- `Retry-After`가 있으면 초 또는 HTTP 날짜 형식을 해석하여 서버의 대기 요청을 반영한다.
- 기본 대기는 2초·4초·8초이며, 동시 재시도를 줄이기 위해 각 대기에 0~1초의 무작위 지연을 더한다.
- 실제 대기는 서버 요청 시간과 기본 대기 중 긴 쪽으로 한다. 실패한 페이지의 날짜·페이지 토큰을 유지한다.
- 최초 요청 외에 페이지당 최대 3회 재시도한다. 성공하면 다음 페이지의 재시도 횟수는 초기화된다.
- 한 번의 대기가 60초를 넘으면 대기 시간을 임의로 줄여 재요청하지 않고 해당 조회를 실패 처리한다.
- 재시도를 소진하거나 긴 대기를 요구받으면 같은 계정 객체의 후속 날짜 조회도 대기 기한 전에는 요청하지 않는다.
  이 대기 상태는 현재 프로세스 메모리에만 보관하며 DB나 인증 정보를 변경하지 않는다.
- 끝내 실패한 날짜는 빈 데이터로 간주하지 않고 부분 결과도 저장하지 않는다.
  자동 수집은 다음 실행에서, 수동 복구는 같은 명령을 재실행하여 다시 처리할 수 있다.
- 이 처리는 SpO₂ 조회에 적용한다. 다른 API와 전체 프로젝트의 호출 제한을 대신 관리하지는 않는다.

## 누락 데이터 수동 복구

변경 파일을 서버에 반영한 뒤, 자동 수집을 재시작하기 전에 실행할 수 있다.
DB 모델 변경이나 마이그레이션은 필요하지 않다.

```bash
docker exec apop python manage.py backfill_spo2 --user-id <USER_ID>
```

기본 범위는 해당 참여자의 연구 시작일(`join_date`)과 참여자 시작 시각 중 늦은 시각부터
실행 시점까지이다. 연구 종료일과 참여자 종료 시각이 있으면 그 범위를 넘지 않는다.
시작일 정보가 모두 없으면 자동으로 범위를 추측하지 않고 오류를 반환한다.
확인된 날짜를 지정할 때는 `--start-date YYYY-MM-DD`, `--end-date YYYY-MM-DD`를 사용한다.
종료일은 해당 날짜를 포함하되 실행 시점 이후의 기록은 저장하지 않는다.

- 날짜별 API 전체 페이지 조회가 성공한 뒤 한 날짜씩 트랜잭션으로 저장한다.
- 같은 분의 여러 표본은 가장 나중 측정된 유효 값으로 합친다.
- 기존 SpO₂ 값은 유지하며, 비어 있는 SpO₂만 채운다. 심박수·걸음 수 등 다른 값은 수정하지 않는다.
- 같은 명령을 반복 실행해도 기존 값을 덮어쓰거나 동일 시각의 행을 중복 생성하지 않는다.
- 고정 Google 계정을 사용하더라도 저장 계정은 지정한 참여자로 한정한다.
- 저장 직전 참여자 정보를 다시 확인한다. 참여 기간이 변경됐으면 중단한다.
- 날짜별 신규 행·기존 행 보완 건수를 출력하고, API에서 확인한 대상 분에 값이 있는지 검증한다.
- 일부 날짜 조회가 실패하면 성공한 날짜는 유지하고 실패 상태로 종료한다. 같은 명령으로 재시도할 수 있다.
- `--dry-run`은 측정 데이터 저장 없이 대상 건수만 확인한다. 인증 토큰은 필요 시 갱신될 수 있다.

## 자동 수집

`sync_daily_data`는 SpO₂를 오늘부터 이전 6일까지, 최근 7일에 대해 재조회한다.
연구 시작일 이전 날짜는 조회하지 않으며, 시작일이 없으면 과거 사용자 기록을 가져오지 않도록 당일만 조회한다.
지연 반영되는 값을 채우기 위한 범위이며 7일보다 오래된 누락은 수동 복구 명령으로 처리한다.
필요하면 Django 설정의 `GOOGLE_HEALTH_SPO2_LOOKBACK_DAYS`로 일수를 조정할 수 있다.

기존 매일 10:00·22:00 배치 일정을 유지하고 CronTrigger의 시간대를 `Asia/Seoul`로 명시한다.
작업의 '오늘' 계산도 운영체제 시간대와 관계없이 한국시간으로 한다.
정기 수집은 API의 최신 값으로 기존 SpO₂를 갱신할 수 있으며, 수동 복구는 누락 값만 채운다.

파일 반영 및 수동 복구 후 기존 스케줄러 컨테이너를 다시 시작해야 자동 수집 코드가 적용된다.

```bash
docker restart scheduler
```

## Git으로 서버 반영

수정 코드와 새 관리 명령 파일을 같은 브랜치에 커밋·푸시한 후 서버에서 실행한다.
프로젝트가 컨테이너의 `/app`에 마운트된 구성을 기준으로 한다.

```bash
cd ~/apop
git pull --ff-only
docker exec apop python manage.py backfill_spo2 --user-id 111
docker restart scheduler
```

복구 명령의 출력에서 실제 시작일이 참여자에 맞는지 확인한다. 종료일 생략 시 실행하는 날까지 처리한다.
기존 프로세스가 변경 코드를 읽도록 스케줄러를 재시작한다. DB 마이그레이션은 필요하지 않다.
